# Реестр экранов и состояний

Единый список того, что игра показывает игроку: экраны, их промежуточные
состояния и способ войти в каждое. Нужен потому, что ревью интерфейса здесь
делают агенты, а агент судит по снятому кадру — состояние, не попавшее в
каталог съёмки (`scripts/screens.ts`), не проверяет никто и никогда.

Отношение трёх файлов друг к другу:

| Файл                 | Что это                                                             |
| -------------------- | ------------------------------------------------------------------- |
| `docs/screens.md`    | **что вообще существует** — этот реестр, источник истины по составу |
| `scripts/screens.ts` | **что снимается** — данные для `npm run shots` и гейта              |
| `shots/index.md`     | **что снято** — индекс к последней съёмке, пишется раннером         |

Правило то же, что у остального `docs/`: новое состояние заводится сюда и в
каталог съёмки тем же изменением, что и сам экран. Колонка «Снимается»
называет `id` из каталога либо ручку, которой не хватает для входа.

Версии — по [ROADMAP](ROADMAP.md). Текущая разрабатываемая — 0.4.0.

---

## А. Обязательное на 0.4.0

Полный цикл: меню → дверь с аппетитом → бой с картами пари и Крупье → расчёт с
near-miss → награда (лавка / Дар) → босс → плата за этаж или торг → итоги.

### А.4 Расчёт (живёт паузой внутри `Fight`)

| Состояние            | Что показывает                                      | Снимается                      |
| -------------------- | --------------------------------------------------- | ------------------------------ |
| Расчёт с пари        | плашки, исход формой, кольцо отсчёта                | `settlement`                   |
| Расчёта нет          | слоты пусты — затемнения нет вовсе                  | `settlement-empty`             |
| Титул «Пауза»        | пари ещё живые: исход не проставлен, куш приглушён  | `settlement`                   |
| Титул «Расчёт»       | пари разрешены: исходы проставлены, выплаты золотом | `settlement-room-end`          |
| Near-miss процентами | метка единицы — две точки столбиком                 | `settlement-near-miss-percent` |
| Near-miss секундами  | кольцо-циферблат вместо процентов                   | `settlement-near-miss-seconds` |
| Четыре формы исхода  | шестиугольник с ядром / кольцо / пустой / крест     | `settlement-outcomes`          |
| Подпись про трамплин | строка ниже кольца, не задевает ряды                | `settlement-leg-up`            |

Экран существует ровно в одном месте забега — в паузе ПЕРЕД первой волной
комнаты: и рендер (`settlementRows`), и пропуск в ядре (`skipSettlement`)
требуют нулевого номера волны при живом `NextWaveAt`. Пауза между волнами
ставит тот же `NextWaveAt` с волной 1 или 2, и расчёта в ней не рисуется вовсе.

Отсюда и два состояния экрана: в паузе первой комнаты пари ещё живые (закрывает
их первая волна), в паузе следующей комнаты они уже разрешены — расчёт делает
`startRoom`. `settle()` удлиняет паузу текущей комнаты, `setRoom(n)` открывает
паузу следующей: разными их делает повод, а не номер волны.

Титул различает эти состояния **по состояниям самих пари** (`BetState.Active`
хотя бы в одной строке — «Пауза», иначе «Расчёт»), см. [UX §Экран
расчёта](UX.md). По номеру волны признак не выражается вовсе: волна здесь
всегда нулевая.

### А.8 Итоги (`RunPhase.Summary`)

| Состояние        | Что показывает                             | Снимается                  |
| ---------------- | ------------------------------------------ | -------------------------- |
| Смерть           | «Ещё разок» доминирует, сид и сборка внизу | `summary-death`            |
| Победа           | титул победы, ключи — главное число        | `summary-victory`          |
| Пол по ключам    | строка «минимум за забег» вместо разбивки  | `summary-death`            |
| Разбивка, смерть | три источника ключей строками, пола нет    | `summary-death-earned`     |
| Разбивка, победа | те же три источника под титулом победы     | `summary-victory-earned`   |
| Near-miss        | подзаголовок «не хватило N%» под титулом   | `summary-victory-nearmiss` |

Строка пола рисуется ровно тогда, когда сумма источников меньше `KEYS.floor`
(`renderer.ts`, `drawSummaryScreen`), а нулевые источники в разбивку не
печатаются вовсе. Смерть в первой комнате — как раз этот случай: пари не
выполнено ни одного, боссов ноль, в кошельке стартовые 30 фишек против ста за
ключ. Поэтому `summary-death` показывает только строку пола.

Из-за этого же правила разбивка требует ОТДЕЛЬНЫХ сценариев: забег, снятый на
первой комнате, не показывает ни одной её строки, и главное число экрана
итогов оставалось необоснованным на всех кадрах. `summary-death-earned` и
`summary-victory-earned` доводят каждый источник до ненулевого вклада по
формуле `keysEarned` (`packages/sim/src/run.ts`, ECONOMY §12): пять выполненных
пари → +1, 250 фишек в кошельке → +2, побеждённый босс → +3, итого 6 ключей.
Числа проверяемы прямо на кадре — строки обязаны сложиться в число сверху.

Два кадра, а не один, потому что титул экрана и разбивка рисуются вместе: на
победе те же строки стоят под другим заголовком, и «разбивка спорит с титулом»
— дефект, который виден только рядом.

`summary-victory-nearmiss` — отдельный сценарий по той же причине: near-miss
рисуется по последнему пари, ставшему `Lost` в тот же тик, что и конец забега
(`Feedback.runEndTick`), а не по любому проигранному за весь забег — такое пари
должно остаться незакрытым до самого конца, и обычный сценарий победы этого не
даёт. Подпись показывается независимо от исхода забега: пари другого игрока
может сорваться тем же тиком, что и победа.

## Б. Реализовано сверх 0.4.0

Кооп на 2–4 игроков рисуется и играется уже сегодня: `newRun({players:N})`
разводит колонки HUD, сжимает плашки при трёх и более, гасит колонку мёртвого.
Снимается: `fight-coop-2`, `fight-coop-3`, `fight-coop-4`, `hud-column-dead`,

общая доля заведения, пинги и эмоции, лобби, клип — в коде отсутствуют.

ролик-статистики, Versus. Кадра у них нет, места в реестре — тоже.

## В. Чего в реестре нет и почему

- **`RunPhase.Settle`** — значение перечисления без единого использования:
  расчёт живёт паузой внутри `Fight`, и сценарии `settlement*` снимают его с
  фазой `Fight`. Отдельного экрана у этой фазы нет.
- **Дверь «Событие»** — тип с нулевым весом, содержания нет ([GDD §5](GDD.md)).
- **Три DOM-оверлея** (обновление, остановка, тост) — рисуются вне канваса,
  `framePng()` их не видит. Проверяются сквозными тестами, а не съёмкой.
- **Особые пари этажей и боссов, красная зона в боссовой комнате** — по GDD в
  0.4.0 их нет.

## Г. Долг: чего в каталоге всё ещё нет

Долга нет: все состояния выше снимаются сценариями из `scripts/screens.ts`.
Закрыта и последняя строка — титул расчёта: он выбирается по состояниям пари, и
оба слова сняты (`settlement` — «Пауза», `settlement-room-end` — «Расчёт»).

Закрыто: точные ресурсы (`setChips`, `setHearts`), покупка (`buy`),
фазы босса и оглушение (`bossPhase`, `damageBoss`), схема ввода (`scheme`),
Крупье целиком (`aceOut`, `aceGesture`, `aceToss`, `bark`), исходы пари
(`failBet`, `winBet`), истекающая карта (`expireCard`), масштаб и поштучный
забор (`uiScale`, `cashoutFocus`), набор дверей (`doorTypes`), телеграфы и
метки (`telegraph`, `spawnMark`), вспышка (`flash`), справка первого забега
(`openTutorial`) и номер комнаты (`setRoom`). Заодно починено найденное при
инвентаризации: `curse(id)` и `take(player)` проверяют аргументы и больше не
делают молча не то, о чём их просили.
