# Double or Die — цикл разработки, запуск и тестирование

_Как запускать, как проверять, как это делает агент. Документ определяет требования к коду, а не только к процессу._

---

## 1. Принцип

**Всё, что можно проверить без графики — проверяется без графики.**

Симуляция детерминирована и не зависит от рендера, поэтому основной инструмент проверки — headless-раннер на Node, который печатает JSON в stdout. Он быстрый, воспроизводимый и одинаково удобен человеку, CI и агенту. Браузер нужен только там, где вопрос действительно визуальный: «красиво ли», «читается ли», «не сломалась ли вёрстка HUD».

Из этого следует требование к архитектуре: **ни одна игровая система не имеет права зависеть от `window`, `document` или Canvas.** Проверяется линтером в CI с первой версии.

## 2. Команды

```bash
npm run dev              # Vite на :5173 — игра в браузере, горячая перезагрузка
npm run sim              # headless-раннер симуляции, JSON в stdout
npm run safety           # достижимость безопасной точки (D4) на каждом тике
npm test                 # юнит + golden-реплеи + сценарии
npm run e2e              # сквозные: игра рисует, бенч рендера под нагрузкой
npm run balance          # Monte-Carlo отчёт, ограничители G1–G17 и D1–D10
npm run assets           # отчёт готовности ассетов и лицензий
npm run bench            # бюджет кадра и производительность
npm run check            # lint + typecheck + границы модулей + палитра + контраст + каталог
npm run check:contrast   # ΔE-проверка пар «карта / игрок / фишка / враг / телеграф / Туз»
npm run build            # веб-сборка
npm run build:desktop    # Electron (появляется в 0.10.0)
```

Каждая команда либо завершается кодом 0 и печатает JSON, либо падает с внятным сообщением. Никаких интерактивных промптов — это ломает и CI, и агента.

## 3. Headless-раннер: главный инструмент

```bash
# Один забег ботом
npm run sim -- --seed 1234 --bot random --json

# Тысяча забегов: ищем зависания и нарушенные инварианты
npm run sim -- --runs 1000 --bot random --json

# Проверка детерминизма: один сид, два прогона, сверка хешей
npm run sim -- --determinism-check --seeds 100

# Переигрывание записанного лога с проверкой хеша
npm run sim -- --replay tests/golden/seed-1-p1.json --assert-hash 0x1234abcd

# Достижимость безопасной точки на каждом тике: ограничитель D4
npm run sim -- --runs 20 --ticks 5400 --bot random --safety --json

# Декларативные сценарии: файл или каталог целиком (см. §5)
npm run sim -- --scenario tests/scenarios

# Сверка эталонных реплеев
npm run golden
```

**Формат вывода** — всегда JSON одной структуры: шапка прогона и массив
забегов под `results`.

```json
{
    "ok": true,
    "runs": 1,
    "failures": 0,
    "bot": "cautious",
    "players": 1,
    "ticks": 1800,
    "results": [
        {
            "seed": 1234,
            "hash": "0x6d095352",
            "ticks": 1800,
            "profile": "cautious",
            "result": {
                "outcome": "alive",
                "room": 1,
                "wave": 1,
                "kills": 26,
                "deaths": 1,
                "hearts": [2],
                "chips": [31]
            },
            "bets": {
                "offered": 6,
                "taken": 4,
                "won": 0,
                "lost": 0,
                "cashed": 4,
                "activeTicks": 606,
                "activeShare": 0.337
            },
            "rooms": { "entered": 2, "completed": 1, "medianTicks": 1242, "ticks": [1242] },
            "errors": []
        }
    ]
}
```

Что здесь есть и чего намеренно нет:

- **`outcome` — `alive` / `dead` / `broken`, и других значений не бывает.** Ни этажа, ни босса, ни экрана итогов до 0.4.0 не существует: забег не кончается, а гибель всех разворачивается перезапуском той же симуляции. Исход из будущего врал бы одинаково во всех тысяче забегов.
- **Кошелёк и сердца — списком по игрокам, не суммой.** Ограничитель G16 сравнивает игроков между собой, а сумма стирает ровно то, что он ищет.
- **Блока `events` нет и не будет в этом виде.** События **выводятся** из состояния, а не эмитятся симуляцией: ядру запрещено аллоцировать в горячем пути, и лог событий на каждый тик — это как раз аллокация (шапка `packages/shared/src/events.ts`). Всё, что известно о забеге, живёт в `Meta` и буферах состояния, и раннер наблюдает за ними снаружи, тик за тиком. Прикладной лог событий — это `[DOD]`-протокол консоли и `__DOD__.events()` в браузере, где аллокации разрешены.
- **`profile` — кем сыгран забег**, а не чем его просили сыграть. У `mixed` имя одно на прогон, а профиль свой на каждый забег, и ограничители считаются по второму: G3 спрашивает про играющего на ставках, G5 — про наглого, G4 — про опытных.
- **`bets.activeShare` и `rooms.medianTicks` считаются уже сейчас**, хотя балансировщик приезжает в 0.4.0: из них считаются G6, G14 и D1, а дописывать наблюдение задним числом дороже — к тому времени рядом будет тысяча золотых прогонов, которые придётся переснимать.

**Боты** — не «ИИ», а простые стратегии для проверки систем. Четыре имени остались с первых версий: `idle` (ничего не делает, доказывает, что игра не зависает сама по себе), `random` (ищет состояния, до которых человек не додумается), `greedy` (берёт все карты, не обналичивает никогда) и `cautious` (одна ближняя карта, тир «Скромно», обналичивает рано). Последний заведён не для полноты набора: ограничитель G14 требует, чтобы через «Забрать» закрывалось 15–35% пари, а без бота, который обналичивает, доля выходила ровно нулевой при любом балансе — ограничитель, который невозможно нарушить, не ограничивает ничего.

Руки у всех четверых идеальные: целятся точно и жмут огонь постоянно. Как верхняя граница поведения это правильно, но **как профиль игрока — нет**: половина порогов ограничителей задана через профили из [ECONOMY §6](ECONOMY.md), а те отличаются друг от друга не только ставками. Поэтому балансовые прогоны идут парой «навык:стратегия»:

```bash
npm run sim -- --runs 500 --bot master:stack --json     # мастер из ECONOMY §6
npm run sim -- --runs 500 --bot median:single --json    # умеренный
npm run sim -- --runs 500 --bot novice:none --json      # осторожный, ноль ставок (G6)
npm run sim -- --runs 1000 --bot mixed --json           # смесь профилей, по одному на забег
```

Навык — `novice` · `median` · `veteran` · `master`, стратегия — `none` · `single` · `stack` · `chips`; числа и доли смеси в [SIMULATION §3](SIMULATION.md). Профиль, которым сыгран забег, стоит в его записи полем `profile`: у `mixed` он свой на каждый забег, и без него отчёт нельзя разложить по ограничителям. Дальше приезжают `келли`, `догоняющий` и `катала` — им нужны механики 0.6.0.

**`--observe` добавляет к каждому забегу разбор**, из которого и считаются ограничители: взятые пари по строковому id, выбранный тир аппетита, исход каждого пари, длительность каждой комнаты с номером этажа и кто отнял сердце.

```bash
npm run sim -- --runs 200 --bot mixed --observe --json
```

```json
"observed": {
    "bets": [{ "player": 0, "id": "no_damage", "stake": 25, "tier": "normal",
               "floor": 1, "room": 3, "takenAt": 1249, "outcome": "won", "resolvedAt": 1790 }],
    "rooms": [{ "floor": 1, "room": 1, "ticks": 1789 }],
    "hits": [{ "player": 0, "tick": 966, "floor": 1, "room": 1, "by": "wedge", "fatal": false }]
}
```

Блок появляется только по флагу, и его отсутствие обязано быть видно: пустой блок в каждом отчёте читался бы как «наблюдали и ничего не нашли». Наблюдение стоит копирования пулов врагов и снарядов перед каждым тиком, и прогонам, которым нужен один хеш, платить за это незачем.

**Источник урона восстанавливается снаружи, а не берётся из ядра.** Запоминать его в состоянии значило бы держать поле в снимке и в хеше ради одной проверки в CI; вместо этого раннер сравнивает арену до тика и после: исчезнувший поджёгший фитиль Фитиль, погасшая вражеская пуля рядом, Клин в фазе тарана вплотную. Оценка честная, а не точная, поэтому `by` умеет говорить `unknown` — D5 и D6 сравнивают доли смертей по врагам, и приписанная вина сдвинула бы обе сильнее, чем признанный пробел.

## 4. Отладочный интерфейс в браузере

При `?debug=1` игра публикует `window.__DOD__` — синхронный API, который агент вызывает через выполнение JavaScript на странице.

Метод появляется вместе с системой, которой он управляет: обещать `warp` до этажей значит потратить час на выяснение, почему он ничего не делает. Версия в третьей колонке — та, в которой метод начинает работать.

| Метод                                 | Что делает                                                                                     | Версия |
| ------------------------------------- | ---------------------------------------------------------------------------------------------- | ------ |
| `ready`                               | промис, резолвится когда игра загружена                                                        | 0.1.0  |
| `newRun({seed, players})`             | начать забег с фиксированным сидом                                                             | 0.1.0  |
| `tick(n?)`                            | продвинуть симуляцию ровно на n тиков (не зависит от времени)                                  | 0.1.0  |
| `play()` / `pause()`                  | обычный ход времени / пауза                                                                    | 0.1.0  |
| `isPaused()`                          | стоит ли время сейчас — без него шаг тиками пришлось бы вести вслепую                          | 0.1.0  |
| `state()`                             | JSON-снимок состояния: игроки, враги, карты на арене, активные пари, кошелёк, Туз              | 0.1.0  |
| `hash()`                              | хеш состояния для сверки                                                                       | 0.1.0  |
| `events(sinceTick?)`                  | структурированный лог событий                                                                  | 0.1.0  |
| `input(player, {move, aim, buttons})` | подать ввод программно; `null` вторым аргументом снимает подмену                               | 0.1.0  |
| `replay()`                            | лог инпутов забега целиком, текстом: принимается `npm run sim -- --replay` как есть            | 0.1.0  |
| `perf()`                              | FPS, число частиц и фигур в последнем кадре                                                    | 0.1.0  |
| `stable(on?)`                         | режим стабильного кадра: выключение вспышек, тряски и хитстопа — для сравнения кадров          | 0.1.0  |
| `render()`                            | нарисовать кадр немедленно, синхронно                                                          | 0.2.0  |
| `mute(on?)`                           | заглушить звук                                                                                 | 0.2.0  |
| `spawn(type, count?)`                 | поставить врагов вокруг игрока: `wedge` / `brick` / `fuse`                                     | 0.2.0  |
| `clear()`                             | убрать с арены всё, кроме игроков                                                              | 0.2.0  |
| `waves(on?)`                          | включить или выключить пополнение арены волнами                                                | 0.2.0  |
| `stress({enemies, particles})`        | нагрузить сцену для замера бюджета кадра                                                       | 0.2.0  |
| `give({chips, hearts}, player?)`      | выдать ресурсы названному игроку; `upgrade` добавляется вместе с магазином в 0.4.0             | 0.2.0  |
| `cards()`                             | что сейчас лежит на арене: id, позиция, владелец, оставшиеся тики                              | 0.3.0  |
| `spawnCard(bet, x, y, owner?)`        | положить карту: `bet` — строка из каталога (`no_damage`, …), без владельца — общая             | 0.3.0  |
| `take(player, cardId?)`               | подобрать карту от лица игрока; без номера — ту, на которой он стоит                           | 0.3.0  |
| `cashout(player, betSlot?)`           | обналичить пари; без номера слота — самое выгодное. Возвращает слот, `q` и выплату             | 0.3.0  |
| `setAppetite(player, tier)`           | задать аппетит                                                                                 | 0.3.0  |
| `frameGrid(cols?, rows?)`             | кадр сеткой средних цветов (по умолчанию 16×9) — снимок картинки для визуальной регрессии (§6) | 0.3.0  |
| `warp({floor, room, boss})`           | прыгнуть в любую точку забега — этажей и боссов нет раньше                                     | 0.4.0  |
| `config(patch)`                       | подменить баланс на лету — требует remote config                                               | 0.11.0 |

Кроме методов интерфейс держит три поля-метки: `build`, `version` и `sha`. Баг-репорт без них бесполезен — «не воспроизводится» чаще всего означает «у нас разные сборки».

**Про Туза `state()` отдаёт не только жест, но и присутствие с точкой стояния**
(`ace.onArena`, `ace.x`, `ace.y`). Одного жеста мало: без признака «он сейчас на
арене» нельзя отличить «Туза нет» от «Туз есть, но неразличим», а разбираться
приходится именно в этом — жалоба звучит одинаково. Отсутствие этой пары полей
однажды стоило вечера: заведение было невидимым, и проверить это было нечем.

### Бюджет кадра меряется в браузере

Симуляция и система частиц меряются в Node (`npm run bench`), но собственно
отрисовка живёт в WebGL, и честно замерить её можно только там, где она
работает. Это делает `npm run e2e` — нагрузка из плана версии (2000 частиц и
200 болванок) прогоняется автоматически и падает, если рендер вылез из
бюджета в 6 мс.

Руками то же самое, когда нужно посмотреть своими глазами:

```js
__DOD__.stress({ enemies: 200, particles: 2000 });
for (let i = 0; i < 30; i++) __DOD__.render(); // прогрев
const t0 = performance.now();
for (let i = 0; i < 120; i++) __DOD__.render();
console.log((performance.now() - t0) / 120, 'мс на кадр', __DOD__.perf());
```

`render()` нужен не только для замера: в невидимой или свёрнутой вкладке
браузер не вызывает `requestAnimationFrame` вовсе, и кадра просто не
существует — а агент проверяет именно картинку.

### Прямая навигация по URL

Любое состояние достижимо одним переходом — это самый дешёвый способ для агента:

```
localhost:5173/?debug=1&seed=1234&scenario=boss_roulette&players=2&autopause=1
```

Параметры: `seed`, `scenario`, `players`, `floor`, `room`, `bets`, `debug`, `autopause`, `stable`, `lang`.

### Протокол консоли

Все игровые события пишутся в консоль с префиксом `[DOD]` и JSON-телом, чтобы их можно было отфильтровать при чтении консоли:

```
[DOD] {"tick":1240,"name":"bet_lost","props":{"id":"no_left_turns","nearMiss":0.87}}
```

Ошибки — с префиксом `[DOD:ERROR]`. Нарушения инвариантов — `[DOD:INVARIANT]`.

### Баг-репорт: файл вместо телеметрии

Телеметрии в 0.4.0 нет ([ROADMAP §0.4.0](ROADMAP.md)), и обратная связь
приходит одним способом: **`F8` складывает баг-репорт в файл**, который тестер
отправляет сам. Никуда не уходит, никакого сервиса на том конце нет —
`packages/client/src/bugreport.ts` собирает JSON и отдаёт его браузеру на
скачивание.

Имя файла — `dod-bug-<сид>-t<тик>-<коммит>.json`: эти три числа спрашивают
первыми, и читаться они обязаны до открытия вложения.

Внутри — лог инпутов забега целиком (тот же формат, что принимает
`npm run sim -- --replay <файл>`), а рядом всё, без чего лог не переигрывается:
версия и коммит сборки, версия протокола и симуляционного конфига, сид, состав,
тик и хеш состояния. Разбор такого репорта — одна команда:

```bash
npm run sim -- --replay <файл> --assert-hash <хеш из репорта>
```

**Набор полей закрытый, и это гейт, а не намерение** ([SECURITY §8](SECURITY.md)):
адреса страницы, строки браузера и содержимого сейва в файле нет, а проверяет
это `tests/bugreport.test.ts` списком ключей. «Заодно пригодится» попадает в
такие файлы само.

**На нарушенном инварианте отчёт собирается сам** — один раз на загрузку
страницы, вместе с плашкой остановки. Просить нажать кнопку в этот момент
значит терять ровно те записи, ради которых уровень инвариантов существует:
игрок видит замерший кадр и первым делом жмёт F5.

## 5. Сценарии: декларативные тесты

Файл JSON, который читается как протокол, а не исполняется как программа.
Написать такой тест дешевле, чем описать баг словами, и читается он потом без
чтения кода.

```json
{
    "name": "Клин объявляет таран телеграфом и только потом бьёт",
    "seed": 1,
    "players": 1,
    "steps": [
        { "spawn": { "type": "клин", "x": 1360, "y": 540 } },
        { "expect": { "enemies": { "min": 1, "max": 1 }, "enemy": { "phase": "idle" } } },
        { "tick": 12 },
        { "expect": { "enemy": { "phase": "telegraph" } } },
        { "tick": 20 },
        { "expect": { "enemy": { "phase": "attack" } } },
        { "tick": 45 },
        { "expect": { "hearts": { "max": 2 } } }
    ]
}
```

Шаги: `input` — подать ввод (действует, пока не сменят), `clearInput` — снять,
`tick` — прошагать, `place` — поставить игрока в точку, `spawn` — поставить
врага, `clear` — очистить арену, `expect` — проверить. Враги и кнопки задаются
именами, а не числами: `["dash"]` и `"клин"` читаются, `2` и `0` — нет, и
опечатка в имени валит сценарий, а не пропускается молча.

**Волны по умолчанию выключены.** Сценарий проверяет одно названное поведение,
и набежавшая волна делает его проверкой чего-то другого: «рывок покрывает
втрое больше ходьбы» перестаёт быть про рывок, стоит на пути оказаться Клину.
Кому волны нужны — тот просит их полем `"waves": true`.

Проверять можно `x`, `y`, `travelled`, `hearts`, `chips`, `alive`,
`invulnerable`, `hash`, а также `enemies`, `bullets`, `chipsOnFloor`, `kills` и
блок `enemy` с полями `index`, `hp`, `x`, `y`, `phase`. Числовые — границами
`min`/`max`, обе необязательны.

Провалы собираются все до единого и печатаются с номером шага и тиком:

```
шаг 3 (тик 120): путь игрока 0 = 621.333, ожидалось ≥ 5000
```

Поля растут вместе с игрой. Каждое пари, каждый враг и каждый босс получают
минимум один сценарий; к 1.0 их будет около двухсот, и они гарантируют, что
балансная правка не сломала логику.

## 6. Пирамида тестирования

**Визуальная регрессия** живёт в `e2e/visual.spec.ts` и бежит вместе с
`npm run e2e`. Ловит она то, чего не видит ни один тест ядра: пропавший слой,
уехавшую камеру, перевёрнутый порядок отрисовки, палитру, съехавшую после
правки одного цвета. Симуляция при всём этом остаётся идеально верной —
ломается ровно картинка.

Сравниваются **не пиксели, а сетка средних цветов 16×9**, и это не экономия
усилий: попиксельный эталон привязан к растеризатору, а их три — SwiftShader
на раннере CI, настоящая видеокарта на машине разработчика и что угодно у
следующего. Такой эталон краснел бы от смены образа раннера, и его перестали
бы читать. Среднее по клетке переживает разницу сглаживания и не переживает
ничего из того, что мы ловим. Допуск — 0.12 по каналу: заметно больше
разброса от сглаживания и россыпи искр (частицы живут в клиенте и
детерминизмом ядра не связаны) и заметно меньше любой настоящей поломки.

Кадр снимает **сам клиент** (`__DOD__.frameGrid`) и рисует его в отдельный
буфер: канвас низколатентный и содержимого после показа не хранит, поэтому
снаружи он читается то верно, то пусто. Сцена — стресс-кадр в `stable()`:
тряска, вспышки и хитстоп выключены, камера стоит, а в кадре обязан быть
каждый слой — пол, колонны, карты, враги, телеграфы, игрок, снаряды, частицы
и HUD. Нагрузка здесь меньше, чем в бенче рендера, намеренно: там меряют
время и берут худшую волну, здесь важна полнота кадра, а не его цена.

Эталон лежит в `e2e/baselines/stress-frame.json`. Первый прогон записывает его
и **честно падает**: молча принять сегодняшнюю картинку за образец — значит
получить проверку, подтверждающую что угодно. Отдельно проверяется, что кадр
неоднороден: равномерная заливка означает, что не нарисовалось ничего.

**Инварианты** — недооценённый уровень. Дешёвые проверки прямо в тике симуляции, включённые в dev-сборке, ловят целый класс багов в момент возникновения, а не через десять минут игры.

Самая содержательная из ставочных проверок — **диапазон схемы ввода**. Схема приезжает двумя битами маски ([TECH §6](TECH.md)), то есть принимает `0..3`, а схем три. Четвёртое значение даёт бит, которого нет ни в одной маске исключений, и матрица «пари × схема ввода» молча перестаёт фильтровать — игрок получает пари, невыполнимое его руками, ровно там, где матрица и заводилась, чтобы этого не случилось. Ошибка не видна ни в бою, ни в логе: она видна только в деньгах, и то не сразу. Тем же уровнем закрыты диапазон аппетита, валидность состояния пари и ссылки на пари, неотрицательность кона и счётчика, валидность жеста Туза, неотрицательность серии смертей и счётчика выходов, и правило «жест не играется на пустой арене».

## 7. Как работает агент

**Порядок предпочтений — от дешёвого к дорогому:**

1. **`npm run sim`** — большинство вопросов о поведении игры отвечается здесь, без браузера, за секунды.
2. **Сценарий** — если вопрос сложнее одной команды, пишется JSON-сценарий и запускается.
3. **Браузер + `__DOD__`** — когда нужно увидеть. Открыть `?debug=1&scenario=...`, вызвать `state()`, снять скриншот.
4. **Живая игра** — только для оценки ощущений, которую агент всё равно не может дать. Это работа человека.

Конфигурация запуска для агента лежит в `.claude/launch.json`:

```json
{
    "version": "0.0.1",
    "configurations": [
        { "name": "dev", "runtimeExecutable": "npm", "runtimeArgs": ["run", "dev"], "port": 5173 }
    ]
}
```

**Правила, делающие игру пригодной для агента** (соблюдаются с версии 0.1.0):

- Ни одной интерактивной команды — всё завершается само.
- Любое состояние игры достижимо через URL-параметры или один вызов отладочного API.
- Всё, что видно на экране, доступно как JSON через `state()`.
- Симуляция шагает по тикам, а не по реальному времени — тесты не зависят от скорости машины.
- Один сид всегда даёт один результат. Без этого агент не может ничего утверждать.

## 8. Правила версионирования

- **Патч** `0.4.1` — исправления и баланс, без новых систем.
- **Минор** `0.5.0` — веха из роадмапа, обязательно с тегом, сборкой и заметками.
- Каждая минорная версия завершается **играбельной сборкой**, даже если она внутренняя.
- Каждая минорная версия добавляет свои сценарии и golden-реплеи — они не удаляются никогда.
- `PROTOCOL_VERSION` и `CONFIG_VERSION` считаются отдельно от версии игры (нужны для совместимости сетевой игры).

## 9. Определение готовности версии

Версия считается готовой, только когда выполнено всё:

1. `npm run check` — чисто.
2. `npm test` — зелено на трёх ОС в CI.
3. `npm run sim -- --runs 1000` — ноль ошибок и зависаний.
4. `npm run bench` — в бюджете кадра.
5. Новые системы покрыты сценариями.
6. Заметки к версии написаны.
7. **Живой плейтест человеком** — версия сыграна руками, а не только ботом.

Пункт 7 не заменяется ничем. Автоматика доказывает, что игра работает; она не доказывает, что в неё интересно играть.
