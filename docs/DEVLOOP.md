# Double or Die — цикл разработки, запуск и тестирование

_Как запускать, как проверять, как это делает агент. Документ определяет требования к коду, а не только к процессу._

---

## 1. Принцип

**Всё, что можно проверить без графики — проверяется без графики.**

Симуляция детерминирована и не зависит от рендера, поэтому основной инструмент проверки — headless-раннер на Node, который печатает JSON в stdout. Он быстрый, воспроизводимый и одинаково удобен человеку, CI и агенту. Браузер нужен только там, где вопрос действительно визуальный: «красиво ли», «читается ли», «не сломалась ли вёрстка HUD».

Из этого следует требование к архитектуре: **ни одна игровая система не имеет права зависеть от `window`, `document` или Canvas.** Проверяется линтером в CI с первой версии.

---

## 2. Команды

```bash
npm run dev              # Vite на :5173 — игра в браузере, горячая перезагрузка
npm run sim              # headless-раннер симуляции, JSON в stdout
npm run safety           # достижимость безопасной точки (D4) на каждом тике
npm test                 # юнит + golden-реплеи + сценарии
npm run e2e              # сквозные: игра рисует, бенч рендера под нагрузкой
npm run balance          # Monte-Carlo отчёт, ограничители G1–G17 и D1–D10
npm run assets           # отчёт готовности ассетов и лицензий
npm run bench            # бюджет кадра и производительность
npm run check            # lint + typecheck + границы модулей + палитра + контраст + каталог
npm run check:contrast   # ΔE-проверка пар «карта / игрок / фишка / враг / телеграф»
npm run build            # веб-сборка
npm run build:desktop    # Electron (появляется в 0.10.0)
```

Каждая команда либо завершается кодом 0 и печатает JSON, либо падает с внятным сообщением. Никаких интерактивных промптов — это ломает и CI, и агента.

## 3. Headless-раннер: главный инструмент

```bash
# Один забег ботом
npm run sim -- --seed 1234 --bot random --json

# Тысяча забегов: ищем зависания и нарушенные инварианты
npm run sim -- --runs 1000 --bot random --json

# Проверка детерминизма: один сид, два прогона, сверка хешей
npm run sim -- --determinism-check --seeds 100

# Переигрывание записанного лога с проверкой хеша
npm run sim -- --replay tests/golden/seed-1-p1.json --assert-hash 0x1234abcd

# Достижимость безопасной точки на каждом тике: ограничитель D4
npm run sim -- --runs 20 --ticks 5400 --bot random --safety --json

# Декларативные сценарии: файл или каталог целиком (см. §5)
npm run sim -- --scenario tests/scenarios

# Сверка эталонных реплеев
npm run golden
```

**Формат вывода** — всегда JSON одной структуры:

```json
{
    "ok": true,
    "seed": 1234,
    "ticks": 54000,
    "hash": "0x8f3a21bc",
    "result": { "outcome": "death", "floor": 2, "room": 5, "chips": 143 },
    "bets": { "offered": 22, "taken": 14, "won": 9, "lost": 5 },
    "events": [{ "tick": 120, "name": "bet_taken", "props": { "id": "no_damage" } }],
    "errors": []
}
```

**Боты** — не «ИИ», а простые стратегии для проверки систем: `idle` (ничего не делает, доказывает, что игра не зависает сама по себе), `random` (ищет состояния, до которых человек не додумается) и `greedy` (берёт все карты, не обналичивает никогда). Дальше приезжают `cautious`, `optimal`, `kelly` и `mixed` — им нужна абстрактная модель, а она появляется в 0.4.0.

## 4. Отладочный интерфейс в браузере

При `?debug=1` игра публикует `window.__DOD__` — синхронный API, который агент вызывает через выполнение JavaScript на странице.

Метод появляется вместе с системой, которой он управляет: обещать `warp` до этажей значит потратить час на выяснение, почему он ничего не делает. Версия в третьей колонке — та, в которой метод начинает работать.

| Метод                                 | Что делает                                                                                | Версия |
| ------------------------------------- | ----------------------------------------------------------------------------------------- | ------ |
| `ready`                               | промис, резолвится когда игра загружена                                                   | 0.1.0  |
| `newRun({seed, players, mode})`       | начать забег с фиксированным сидом                                                        | 0.1.0  |
| `tick(n)`                             | продвинуть симуляцию ровно на n тиков (не зависит от времени)                             | 0.1.0  |
| `play()` / `pause()`                  | обычный ход времени / пауза                                                               | 0.1.0  |
| `state()`                             | JSON-снимок состояния: игроки, враги, карты на арене, активные пари, кошелёк              | 0.1.0  |
| `hash()`                              | хеш состояния для сверки                                                                  | 0.1.0  |
| `events(sinceTick?)`                  | структурированный лог событий                                                             | 0.1.0  |
| `input(player, {move, aim, buttons})` | подать ввод программно                                                                    | 0.1.0  |
| `perf()`                              | FPS, число частиц и фигур в последнем кадре                                               | 0.1.0  |
| `stable()`                            | режим стабильного кадра: выключение вспышек, тряски и хитстопа — для сравнения скриншотов | 0.1.0  |
| `render()`                            | нарисовать кадр немедленно, синхронно                                                     | 0.1.0  |
| `mute(on)`                            | заглушить звук                                                                            | 0.1.0  |
| `spawn(type, count)`                  | поставить врагов вокруг игрока: `wedge` / `brick` / `fuse`                                | 0.2.0  |
| `clear()`                             | убрать с арены всё, кроме игроков                                                         | 0.2.0  |
| `waves(on)`                           | включить или выключить пополнение арены волнами                                           | 0.2.0  |
| `stress({enemies, particles})`        | нагрузить сцену для замера бюджета кадра                                                  | 0.2.0  |
| `give({chips, hearts})`               | выдать ресурсы; `upgrade` добавляется вместе с магазином в 0.4.0                          | 0.2.0  |
| `cards()`                             | что сейчас лежит на арене: id, позиция, владелец, оставшиеся тики                         | 0.3.0  |
| `spawnCard(id, x, y, owner?)`         | положить карту (без владельца — общая)                                                    | 0.3.0  |
| `take(player, cardId)`                | подобрать карту от лица игрока                                                            | 0.3.0  |
| `cashout(player, betId)`              | обналичить пари; возвращает `q` и выплату                                                 | 0.3.0  |
| `setAppetite(player, tier)`           | задать аппетит                                                                            | 0.3.0  |
| `warp({floor, room, boss})`           | прыгнуть в любую точку забега — этажей и боссов нет раньше                                | 0.4.0  |
| `config(patch)`                       | подменить баланс на лету — требует remote config                                          | 0.11.0 |

### Бюджет кадра меряется в браузере

Симуляция и система частиц меряются в Node (`npm run bench`), но собственно
отрисовка живёт в WebGL, и честно замерить её можно только там, где она
работает. Это делает `npm run e2e` — нагрузка из плана версии (2000 частиц и
200 болванок) прогоняется автоматически и падает, если рендер вылез из
бюджета в 6 мс.

Руками то же самое, когда нужно посмотреть своими глазами:

```js
__DOD__.stress({ enemies: 200, particles: 2000 });
for (let i = 0; i < 30; i++) __DOD__.render(); // прогрев
const t0 = performance.now();
for (let i = 0; i < 120; i++) __DOD__.render();
console.log((performance.now() - t0) / 120, 'мс на кадр', __DOD__.perf());
```

`render()` нужен не только для замера: в невидимой или свёрнутой вкладке
браузер не вызывает `requestAnimationFrame` вовсе, и кадра просто не
существует — а агент проверяет именно картинку.

### Прямая навигация по URL

Любое состояние достижимо одним переходом — это самый дешёвый способ для агента:

```
localhost:5173/?debug=1&seed=1234&scenario=boss_roulette&players=2&autopause=1
```

Параметры: `seed`, `scenario`, `players`, `floor`, `room`, `bets`, `debug`, `autopause`, `stable`, `lang`.

### Протокол консоли

Все игровые события пишутся в консоль с префиксом `[DOD]` и JSON-телом, чтобы их можно было отфильтровать при чтении консоли:

```
[DOD] {"tick":1240,"name":"bet_lost","props":{"id":"no_left_turns","nearMiss":0.87}}
```

Ошибки — с префиксом `[DOD:ERROR]`. Нарушения инвариантов — `[DOD:INVARIANT]`.

## 5. Сценарии: декларативные тесты

Файл JSON, который читается как протокол, а не исполняется как программа.
Написать такой тест дешевле, чем описать баг словами, и читается он потом без
чтения кода.

```json
{
    "name": "Клин объявляет таран телеграфом и только потом бьёт",
    "seed": 1,
    "players": 1,
    "steps": [
        { "spawn": { "type": "клин", "x": 1360, "y": 540 } },
        { "expect": { "enemies": { "min": 1, "max": 1 }, "enemy": { "phase": "idle" } } },
        { "tick": 12 },
        { "expect": { "enemy": { "phase": "telegraph" } } },
        { "tick": 20 },
        { "expect": { "enemy": { "phase": "attack" } } },
        { "tick": 45 },
        { "expect": { "hearts": { "max": 2 } } }
    ]
}
```

Шаги: `input` — подать ввод (действует, пока не сменят), `clearInput` — снять,
`tick` — прошагать, `place` — поставить игрока в точку, `spawn` — поставить
врага, `clear` — очистить арену, `expect` — проверить. Враги и кнопки задаются
именами, а не числами: `["dash"]` и `"клин"` читаются, `2` и `0` — нет, и
опечатка в имени валит сценарий, а не пропускается молча.

**Волны по умолчанию выключены.** Сценарий проверяет одно названное поведение,
и набежавшая волна делает его проверкой чего-то другого: «рывок покрывает
втрое больше ходьбы» перестаёт быть про рывок, стоит на пути оказаться Клину.
Кому волны нужны — тот просит их полем `"waves": true`.

Проверять можно `x`, `y`, `travelled`, `hearts`, `chips`, `alive`,
`invulnerable`, `hash`, а также `enemies`, `bullets`, `chipsOnFloor`, `kills` и
блок `enemy` с полями `index`, `hp`, `x`, `y`, `phase`. Числовые — границами
`min`/`max`, обе необязательны.

Провалы собираются все до единого и печатаются с номером шага и тиком:

```
шаг 3 (тик 120): путь игрока 0 = 621.333, ожидалось ≥ 5000
```

Поля растут вместе с игрой. Каждое пари, каждый враг и каждый босс получают
минимум один сценарий; к 1.0 их будет около двухсот, и они гарантируют, что
балансная правка не сломала логику.

## 6. Пирамида тестирования

| Уровень            | Инструмент                 | Что ловит                                                             | Когда бежит                 |
| ------------------ | -------------------------- | --------------------------------------------------------------------- | --------------------------- |
| Юнит               | Vitest                     | fixed-point математика, RNG, формулы экономики                        | каждое сохранение           |
| **Golden-реплеи**  | `npm test`                 | **слом детерминизма** — самый опасный класс багов                     | каждый коммит, 3 ОС         |
| Сценарии           | headless                   | логика пари, врагов, боссов                                           | каждый коммит               |
| Ботовые прогоны    | headless                   | зависания, недостижимые состояния, разъехавшаяся экономика            | каждую ночь, 10 000 забегов |
| Инварианты         | в рантайме                 | «HP не отрицательный», «кошелёк не отрицательный», «врагов ≤ потолка» | всегда в dev-сборке         |
| Производительность | `npm run bench`            | выход за бюджет кадра                                                 | каждый коммит               |
| Баланс             | `npm run balance`          | экономика вне границ ([ECONOMY.md §13](ECONOMY.md))                   | на каждой правке чисел      |
| Визуальные         | стресс-кадр в `stable()`   | пропавший слой, уехавшая камера, сбитая палитра                       | каждый коммит               |
| Контраст           | `npm run check:contrast`   | цвета, которые игрок перестал различать                               | каждый коммит               |
| Ассеты             | `npm run assets`           | пропавший файл, неуказанная лицензия                                  | каждый коммит               |
| Живые              | человек и агент в браузере | «весело ли» — единственное, что не автоматизируется                   | постоянно                   |

**Визуальная регрессия** сравнивает не пиксели, а сетку средних цветов 16×9:
эталонный скриншот привязан к растеризатору, а их три — SwiftShader на
раннере, настоящая видеокарта на машине разработчика и что угодно у
следующего. Попиксельный эталон краснел бы от смены образа раннера, и его
перестали бы читать. Кадр снимает сам клиент (`__DOD__.frameGrid`) и рисует
его в отдельный буфер: канвас низколатентный и содержимого после показа не
хранит, поэтому снаружи он читается то верно, то пусто.

**Инварианты** — недооценённый уровень. Дешёвые проверки прямо в тике симуляции, включённые в dev-сборке, ловят целый класс багов в момент возникновения, а не через десять минут игры.

## 6А. Матрица покрытия: что именно закрыто автотестами

Цель — чтобы вручную проверялось только «весело ли». Всё остальное обязано ловиться машиной.

### Ядро симуляции

| Область                | Проверка                                                                                                | Версия |
| ---------------------- | ------------------------------------------------------------------------------------------------------- | ------ |
| Fixed-point математика | сложение, умножение, деление, корень, тригонометрия против эталона; отсутствие переполнений на границах | 0.1.0  |
| RNG                    | воспроизводимость, независимость семи потоков, равномерность распределения                              | 0.1.0  |
| **Детерминизм**        | 20 golden-реплеев × 3 ОС, сверка хеша каждые 600 тиков                                                  | 0.1.0  |

### Правило покрытия

**Новая механика не считается готовой без сценария.** Пари без теста, враг без проверки автомата, миграция без прогона — незакрытая работа, а не «потом допишем». Сценарии и golden-реплеи только накапливаются и никогда не удаляются.

## 7. Как работает агент

**Порядок предпочтений — от дешёвого к дорогому:**

1. **`npm run sim`** — большинство вопросов о поведении игры отвечается здесь, без браузера, за секунды.
2. **Сценарий** — если вопрос сложнее одной команды, пишется JSON-сценарий и запускается.
3. **Браузер + `__DOD__`** — когда нужно увидеть. Открыть `?debug=1&scenario=...`, вызвать `state()`, снять скриншот.
4. **Живая игра** — только для оценки ощущений, которую агент всё равно не может дать. Это работа человека.

Конфигурация запуска для агента лежит в `.claude/launch.json`:

```json
{
    "version": "0.0.1",
    "configurations": [
        { "name": "dev", "runtimeExecutable": "npm", "runtimeArgs": ["run", "dev"], "port": 5173 }
    ]
}
```

**Правила, делающие игру пригодной для агента** (соблюдаются с версии 0.1.0):

- Ни одной интерактивной команды — всё завершается само.
- Любое состояние игры достижимо через URL-параметры или один вызов отладочного API.
- Всё, что видно на экране, доступно как JSON через `state()`.
- Симуляция шагает по тикам, а не по реальному времени — тесты не зависят от скорости машины.
- Один сид всегда даёт один результат. Без этого агент не может ничего утверждать.

## 8. Правила версионирования

- **Патч** `0.4.1` — исправления и баланс, без новых систем.
- **Минор** `0.5.0` — веха из роадмапа, обязательно с тегом, сборкой и заметками.
- Каждая минорная версия завершается **играбельной сборкой**, даже если она внутренняя.
- Каждая минорная версия добавляет свои сценарии и golden-реплеи — они не удаляются никогда.
- `PROTOCOL_VERSION` и `CONFIG_VERSION` считаются отдельно от версии игры (нужны для совместимости сетевой игры).

## 9. Определение готовности версии

Версия считается готовой, только когда выполнено всё:

1. `npm run check` — чисто.
2. `npm test` — зелено на трёх ОС в CI.
3. `npm run sim -- --runs 1000` — ноль ошибок и зависаний.
4. `npm run bench` — в бюджете кадра.
5. Новые системы покрыты сценариями.
6. Заметки к версии написаны.
7. **Живой плейтест человеком** — версия сыграна руками, а не только ботом.

Пункт 7 не заменяется ничем. Автоматика доказывает, что игра работает; она не доказывает, что в неё интересно играть.
