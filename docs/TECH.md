# Double or Die — техническая архитектура

_Версия 1.0. Решения помечены как «принято» или «к проверке спайком»._

---

## 1. Главное архитектурное решение

**Симуляция игры — чистый детерминированный TypeScript-модуль без единой зависимости, не знающий ни про рендер, ни про инпут, ни про сеть.**

```
┌──────────────────────────────────────────────────────────┐
│  ОБОЛОЧКА (Electron / браузер / Capacitor)               │
├──────────────────────────────────────────────────────────┤
│  ПЛАТФОРМЕННЫЙ СЛОЙ                                       │
│  Steamworks · сохранения · телеметрия · транспорт сети    │
├──────────────────────────────────────────────────────────┤
│  СЛОЙ ПРЕДСТАВЛЕНИЯ                                       │
│  Renderer (WebGL2) · Audio · Input · UI · интерполяция    │
├──────────────────────────────────────────────────────────┤
│  ЯДРО СИМУЛЯЦИИ  ◄── чистый TS, 0 зависимостей            │
│  fixed-point математика · SoA typed arrays · 60 Гц тик    │
│  вход: InputFrame[] + seed   выход: State + StateHash     │
└──────────────────────────────────────────────────────────┘
```

**Что это даёт бесплатно:**

| Возможность               | Как получается                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| Реплеи                    | лог инпутов (~100 КБ на забег после сжатия) переигрывается один-в-один                     |
| Дейли-таблицы с античитом | сервер переигрывает лог и сверяет хеш состояния                                            |
| Golden-тесты              | записанный лог + ожидаемый хеш ловит любой слом детерминизма                               |
| Monte-Carlo балансировка  | 100 000 забегов: абстрактной моделью (SIMULATION.md §2) — минуты, полной симуляцией — часы |
| Онлайн-мультиплеер        | lockstep и rollback возможны только при детерминизме                                       |
| Отладка багов             | баг-репорт = лог инпутов, воспроизводится точно                                            |
| Порт на консоли           | ядро — спецификация, golden-реплеи валидируют порт                                         |

Это единственное решение, которое **невозможно принять позже**. Всё остальное можно переделать.

## 2. Детерминизм: как именно

### 2.1 Запрещено в ядре симуляции

```ts
Math.random()      Date.now()       performance.now()
Math.sin/cos/tan/atan2/pow/exp      // не специфицированы стандартом!
Object/Map итерация как источник порядка
Array.sort без полного компаратора
float-накопление позиций
секунды в любом виде                // все тайминги — только в тиках
```

**Никаких секунд в конфиге симуляции.** «Карта тает за 12 секунд» существует в коде как `720 тиков`, «окно Удвоим 3 секунды» — как `180 тиков`. Секунды допустимы только в текстах для людей.

### 2.2 Математика

**Fixed-point Q16.16** для всех величин симуляции (позиции, скорости, углы, HP).
Причина: IEEE-754 гарантирует детерминизм для `+ - * / sqrt`, но `Math.sin`, `Math.cos`, `Math.atan2` **не специфицированы** и реально различаются между V8, JavaScriptCore и SpiderMonkey. Одно расхождение в последнем бите — и через 30 секунд у двух игроков разные миры.

- Тригонометрия — таблицы на 4096 значений с линейной интерполяцией в fixed-point.
- квадратный корень — целочисленный алгоритм Ньютона.
- Все константы — целые в единицах Q16.16.
- **Умножение и деление — через BigInt-свободное hi/lo-разбиение:** произведение двух Q16.16 требует 64-битного промежуточного значения, которое не влезает ни в `Math.imul`, ни в 53-битную мантиссу float64. Квадраты дистанций на арене Q16.16 переполняют в принципе — диагональ в квадрате это миллионы против потолка 32767, — поэтому длина считается `length()`, который уходит в обычные числа и возвращается обратно. Анализ диапазонов закреплён тестом `tests/ranges.test.ts`; отдельный формат Q24.8 по его итогам не нужен нигде.

### 2.3 RNG

`xoshiro128**`, сидованный. **Семь независимых потоков** — `layout`, `waves`, `bets`, `cards`, `loot`, `shop`, `combat`. Разделение обязательно: иначе правка любой системы ломает сиды всех остальных, и дейли перестают воспроизводиться между версиями.

Поток `combat` отвечает за мелкую случайность внутри боя: разброс выстрела, направление отскока фишки. Отдельно от `waves` он именно потому, что стреляет ИГРОК: привяжи разброс к потоку волн — и число выстрелов начнёт менять состав следующей волны, один и тот же сид даст разные комнаты в зависимости от того, как играл человек, и воспроизвести баг-репорт станет нечем.

Поток `cards` отвечает за раскладку карт пари на арене и за подбросы Туза. Выбор точки подброса — **чистая функция от состояния симуляции** (позиции игроков, зоны телеграфов, сальдо игрока с Тузом), а не обращение к общему RNG: «Туз кладёт карту в опасное место» должно воспроизводиться в реплее один в один.

### 2.4 Хранение состояния

Struct-of-Arrays на `Int32Array` / `Uint8Array`, всё предаллоцировано под потолки (200 врагов, 800 снарядов, 2000 частиц, 8 карт пари, 1 Туз). Карты и Туз — полноценные сущности симуляции и входят в снимок состояния и в его хеш. Ноль аллокаций в горячем пути — иначе GC-пауза съест кадр. Снимок состояния = `set()` на пару типизированных массивов, ~120 КБ, копируется за ~0.02 мс. Это делает откаты (rollback) дешёвыми.

### 2.5 Проверка

- **Golden-реплеи в CI:** 20 записанных забегов, каждый прогоняется, сверяется хеш каждые 600 тиков. Любой слом детерминизма падает на PR.
- **Реплей = сид + инпуты + версия симуляционного конфига.** Балансная правка меняет конфиг и легально ломает хеши старых реплеев — поэтому каждый golden привязан к своему снапшоту конфига и продолжает проходить. Изменение _логики_ требует осознанного ре-бейзлайна с записью в заметки версии; молчаливое обновление хешей запрещено.
- **Кросс-платформенная проверка:** те же реплеи прогоняются на Windows/macOS/Linux в матрице CI. Расхождение = красная сборка.

### 3А. Инфраструктура: один VPS — решение, а не компромисс

**Вся серверная часть живёт на одном VPS владельца проекта до ~1000 одновременных игроков** — и, если игра не станет большим успехом, так останется навсегда. Это возможно потому, что игра спроектирована почти без бэкенда: мультиплеер — P2P, всё работает оффлайн, валидация реплеев асинхронна. Один сервер за $10–20/мес закрывает всё.

```
VPS (Docker Compose)
├─ nginx          — TLS, реверс-прокси, статика веб-сборки
├─ Node (Fastify) — ingest телеметрии, лидерборды, remote config,
│                   сигналинг WebRTC (WebSocket), админка
├─ SQLite         — все данные: события, таблицы, конфиг, аудит-лог;
│                   litestream → off-site бэкап
├─ replay-worker  — отдельный процесс валидации реплеев: очередь в SQLite,
│                   жёсткие timeout и приоритет, не мешает основному сервису
└─ coturn         — TURN-релей для веб-мультиплеера
```

**Правила простоты (нарушение — повод для ревью):**

- Никаких Kubernetes, брокеров очередей, микросервисов, managed-баз, serverless. Одна Node-аппка, одна SQLite, один compose-файл.
- Нагрузочная цель — **сотни** одновременных игроков. Архитектура под высокие нагрузки до релиза не строится вовсе.
- Деплой бэкенда — `git pull && docker compose up -d`. Откат — предыдущий тег образа.
- Мониторинг на старте — healthcheck-эндпоинт + бесплатный внешний uptime-пинг + логи compose. Grafana OSS ставится на тот же VPS в 0.11.0, когда появляются данные.

**Путь роста — только если игра выстрелила (>1000 CCU):** SQLite → Postgres, второй VPS под TURN, дальше по фактическому узкому месту. Облачный serverless-стек — опция из этого будущего, не план. Готовность к нему обеспечена одним свойством: бэкенд — обычная переносимая Node-аппка.

**Отвергнуто и почему:**

- _Godot/Unity_ — веб-стек даёт мгновенный цикл итераций и играбельную ссылку вместо `.exe`; это перевешивает нативность.
- _Tauri v1/v2 для десктопа 1.0_ — системный вебвью означает WebKitGTK на Linux и Steam Deck, где WebGL-производительность нестабильна. Для игры на 60 FPS консистентность рантайма важнее размера бинарника. **Пересмотреть после 1.0** (Tauri даёт 8 МБ вместо 150 МБ и мобильные платформы).
- _Canvas 2D_ — не тянет 2000 частиц с обводками; WebGL2 обязателен.
- _React/Vue для игрового UI_ — DOM-оверлей ломает геймпад-фокус и добавляет кадровую задержку.

Веб — не «демо-версия», а первая и самая долгоживущая цель: вся разработка и вся альфа идут в браузере, оболочка Electron появляется только когда понадобится Steam.

### Консоли — честно

Electron на консоли не портируется. Два реальных пути, оба после 1.0:

1. **Порт ядра на нативный движок** (Godot 4 + C#/GDScript или свой Rust-рендерер). Ядро симуляции — чистая логика без зависимостей, переписывается механически, а **golden-реплеи доказывают идентичность порта**. Это и есть главная выгода от §1.
2. **Портирующая студия** (порт-хаус) — платим, они делают, обычно из нативной кодовой базы.

**Решение зафиксировать до 1.0:** если консоли в планах всерьёз, ядро симуляции с самого начала пишется в подмножестве TS, тривиально транслируемом в C# (без замыканий в горячем пути, без итераторов, только структуры и массивы). Стоит дёшево сейчас, экономит месяцы потом.

## 5. Производительность

**Бюджет кадра при 60 FPS (16.6 мс):**

| Этап                              | Бюджет                             |
| --------------------------------- | ---------------------------------- |
| Симуляция (1 тик)                 | ≤ 0.4 мс в среднем, ≤ 1 мс пиковый |
| Откаты — **резерв, с версии 1.1** | ≤ 4 мс (8 × 0.4 + копия снимка)    |
| Рендер                            | ≤ 6 мс                             |
| Аудио + прочее                    | ≤ 1 мс                             |
| Запас                             | ≥ 2 мс                             |

**Целевое железо:** Steam Deck и интегрированная графика пятилетней давности — 60 FPS в 1080p при полной арене.

**Правила:**

- Ноль аллокаций в кадре (пулы объектов на всё: снаряды, частицы, урон-числа).
- Один draw call на слой через батчинг; фигуры запекаются в атлас при старте.
- Частицы — инстансинг, обновляются в типизированных массивах.
- Симуляция и рендер разделены: тик фиксирован 60 Гц, рендер интерполирует между тиками (поддержка 120/144 Гц мониторов бесплатно).
- Автопрофилирование в билде: если 1% low падает ниже 50 FPS — телеметрия шлёт событие с конфигурацией железа.

## 6. Инпут

Все источники нормализуются в единую структуру **до** попадания в симуляцию:

```ts
type InputFrame = {
    move: FixedVec2; // нормализованный вектор
    aim: FixedVec2; // нормализованный вектор
    buttons: number; // 16-битная маска, см. ниже
};
```

**Битовая маска — часть протокола и формата реплея.** Любое новое действие обязано попасть сюда, иначе оно физически не существует ни для сети, ни для golden-тестов:

| Бит   | Действие                                                    |
| ----- | ----------------------------------------------------------- |
| 0     | `fire` — огонь                                              |
| 1     | `dash` — рывок                                              |
| 2     | `take` — подтвердить подбор карты                           |
| 3     | **`cashout`** — «Забрать»                                   |
| 4     | **`inspect`** — рассмотреть карту (удержание)               |
| 5     | `accept` — принять «Удвоим?»                                |
| 6     | `decline` — отказаться                                      |
| 7     | `revive` — воскрешение напарника (удержание)                |
| 8–9   | **`appetite`** — аппетит: скромно / нормально / по-крупному |
| 10    | `ping`                                                      |
| 11–13 | `emote` (8 эмоций)                                          |
| 14–15 | резерв                                                      |

Тик передаётся неявно позицией в потоке. Полезная нагрузка — 6 байт на кадр; сырой лог забега ≈ 320 КБ, RLE-сжатие неизменных кадров даёт 50–120 КБ.

Маска входит в `PROTOCOL_VERSION` и в версию формата реплея: её изменение делает старые реплеи и старых клиентов несовместимыми **явно**, а не через десинк.

| Источник          | Реализация                                                      |
| ----------------- | --------------------------------------------------------------- |
| Геймпад           | Gamepad API + **Steam Input** (глифы, ремап, любые контроллеры) |
| Клавиатура + мышь | WASD + прицел мышью (самое точное)                              |
| Только клавиатура | WASD + стрелки/IJKL, авто-прицел «лёгкий» по умолчанию          |
| Тач               | виртуальные стики, автоогонь                                    |

**Мёртвые зоны:** радиальная 0.18 с ремапом остатка в 0..1 (не квадратная — иначе диагонали врут).
**Буфер ввода:** 6 кадров на рывок и подтверждения — прощает ранние нажатия.
**Coyote-время** на рывок: 4 кадра.

Подробности удобства и доступности — в [UX.md](UX.md).

## 7. Мультиплеер

### 7.1 Модель

Топология — **host-authoritative peer-to-peer**, 1–4 игрока.

- **Бой** — детерминированная симуляция, синхронизируемая инпутами.
- **Мета** (магазин, выбор двери, расчёт) — авторитет хоста, простые RPC. Здесь микрозадержка не важна, а простота важна. **Итог меты сериализуется как инпут-событие на границе комнаты и входит в детерминированное состояние и его хеш** — граница мета/симуляция не может стать источником десинков, а состояние меты переживает смену хоста.
- **Барьер старта комнаты.** Аппетит выбирается в мете, но влияет на бой, поэтому комната не стартует, пока аппетиты всех живых игроков не зафиксированы инпут-событием на общем тике. Не ответившему по таймауту присваивается его прошлый аппетит.

### 7.1А Замедление времени и мультиплеер

Слоу-мо при «Удвоим?» и при разглядывании карты **несовместимо с lockstep**: если оно меняет темп симуляции, один игрок тормозит всё лобби и получает время подумать за чужой счёт; если это чистый рендер-эффект, восприятие расходится с реальными тиками.

Правило: **темп симуляции постоянен всегда.**

| Режим          | Поведение                                                                                                                        |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Соло           | слоу-мо настоящее — темп симуляции падает до 20%                                                                                 |
| Локальный кооп | слоу-мо общее для всех (экран один), с кулдауном на разглядывание карты                                                          |
| Онлайн         | замедления нет: «Удвоим?» — окно решения в реальном времени, разглядывание карты разворачивает карточку в HUD без влияния на бой |

### 7.2 Синхронизация: два этапа

**Этап 1 — Lockstep с адаптивной задержкой ввода (0.9.0, кооп).**
Все клиенты симулируют одинаково, обмениваясь только инпутами. Задержка ввода подстраивается под худший пинг лобби (2–6 кадров, 33–100 мс). Для PvE-кооп-твин-стика это приемлемо и **несравнимо проще в отладке**.

**Этап 2 — Rollback (версия 1.1, вместе с онлайн-Versus).**
Предсказываем чужие инпуты, при расхождении откатываемся и пересимулируем. Наши снимки состояния стоят 0.02 мс, откат на 8 кадров — 0.2 мс. Локальный ввод становится мгновенным.

Архитектура едина: и то, и другое требует ровно детерминизма и снимков. Переход между ними не меняет игровой код.

### 7.3 Транспорт

Абстракция `Transport` с двумя реализациями:

| Реализация               | Где            | Детали                                                                                                                                                                       |
| ------------------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Steam Networking Sockets | Steam-сборки   | NAT-обход и релеи Valve бесплатно, ноль серверных затрат                                                                                                                     |
| WebRTC DataChannel       | веб, мобильные | unreliable+unordered для инпутов, reliable для меты; сигналинг — WebSocket на VPS; **только через TURN-релей** (coturn на VPS, SECURITY §4.1) с короткоживущими HMAC-кредами |

### 7.4 Устойчивость (это и есть «стабильный мультиплеер»)

| Механизм                  | Реализация                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Обнаружение десинка**   | хеш состояния (FNV-1a по массивам) каждые 30 тиков, сверка со всеми пирами                                                                                                                                                                                                                                                                                                         |
| **Реакция на десинк**     | снимок **большинства** (совпадающие хеши) рассылается меньшинству — хост не привилегирован, злонамеренный хост не может навязать сфабрикованное состояние; повторный десинк одного пира в публичном лобби — кик; событие телеметрии с логами для посмертного разбора                                                                                                               |
| **Потеря пакетов**        | инпуты избыточно дублируются за 3 последних кадра в каждом пакете — потеря одного пакета невидима                                                                                                                                                                                                                                                                                  |
| **Обрыв связи**           | 5 секунд удержания, игрок управляется «заглушкой» (стоит на месте, неуязвим); успел вернуться — продолжает, нет — становится Духом                                                                                                                                                                                                                                                 |
| **Уход хоста**            | full mesh между пирами (не звезда через хоста — иначе обрыв хоста рвёт все каналы); мета входит в детерминированное состояние (§7.1), поэтому новый хост (наименьший ID) продолжает без потери; спайк миграции — перед 0.9.0                                                                                                                                                       |
| **Отставший клиент**      | если пир не успевает симулировать, лобби замедляется на ≤10%; при систематическом отставании — предложение снизить графику                                                                                                                                                                                                                                                         |
| **Несовместимые версии**  | `PROTOCOL_VERSION` проверяется при рукопожатии, понятное сообщение вместо десинка                                                                                                                                                                                                                                                                                                  |
| **Фоновая вкладка (веб)** | rAF и таймеры в свёрнутой вкладке замораживаются — один альт-табнувший игрок остановил бы лобби. Симуляция живёт в Web Worker (троттлится мягче), по `visibilitychange` игрок переводится в «заглушку»; сетевой тест «вкладка в фоне 30 секунд» обязателен                                                                                                                         |
| **Гонка за картой**       | два игрока могут коснуться карты в одном тике. Разрешение детерминированное: побеждает меньшая дистанция до центра карты, при равенстве — меньший номер игрока. Карта помечается занятой в тот же тик. Подбор требует **подтверждения кнопкой** (`take`), а не срабатывает касанием — дискретное событие разрешается однозначно и не навязывает пари тому, кто просто уворачивался |
| **Поздние инпуты**        | инпут за уже отсимулированный тик **отбрасывается безусловно**, игрок получает за тот кадр «заглушку». Иначе пир, придерживающий отправку, выигрывает гонку за карту и обналичивает пари после того, как увидел урон                                                                                                                                                               |
| **Пауза**                 | в кооп-онлайне паузы нет; есть «перекур» — голосование, максимум 2 раза за забег                                                                                                                                                                                                                                                                                                   |

### 7.5 Трафик

Инпут-кадр 6 байт × 4 игрока × 60 Гц ≈ **1.4 КБ/с** на пира до накладных расходов. Мультиплеер практически бесплатен по трафику — прямое следствие детерминизма.

### 7.6 Античит

- **Лидерборды:** клиент отправляет лог инпутов + сид. Replay-worker на VPS переигрывает симуляцию headless и сверяет итоговый хеш. Подделать результат = невозможно без честной игры.
- **Кооп:** доверяем (это игра с друзьями), но у хоста есть кик.
- **Versus онлайн:** авторитет хоста + валидация реплеем после матча.

## 8. Сборка, обновления и патчинг

### 8.1 Почему у нас будут маленькие патчи

**В игре нет растровых ассетов геймплея** — всё рисуется кодом. Полезная нагрузка игры — это несколько мегабайт JS плюс аудио. Значит, типичный патч баланса — **1–5 МБ**.

### 8.2 Раскладка депо Steam

Три депо с разной частотой изменений — это ключ к быстрым обновлениям:

| Депо      | Содержимое                 | Частота       | Размер  |
| --------- | -------------------------- | ------------- | ------- |
| `runtime` | Electron/Chromium          | раз в квартал | ~150 МБ |
| `game`    | JS-бандл, шейдеры, конфиги | каждый патч   | ~6 МБ   |
| `audio`   | музыка и сэмплы            | редко         | ~40 МБ  |

Steam делает чанковый дельта-патчинг; условия его работы перечислены один раз в §8.7 — канонический список, здесь не дублируется. Итог: игрок получает балансный патч за секунды.

### 8.3 Обновления без патча — и почему конфиг делится надвое

Числовой баланс живёт в **remote config** (см. OPS.md §5), а не в коде: коэффициенты пари, цены, бюджеты волн правятся без сборки и без загрузки.

Но здесь прячется противоречие, которое ломает кооп. Постепенный раскат — стандартная хорошая практика: выкатили новые числа на 5% игроков, посмотрели метрики, поехали дальше. Проблема в том, что **конфиг влияет на детерминированную симуляцию**, а значит эти 5% физически не могут играть с остальными 95%: у них разойдутся миры. Раскат по процентам фрагментирует и без того небольшой пул игроков и выглядит для них как «мы с другом не можем зайти в одно лобби».

Поэтому конфиг разделён на два класса с разными правилами:

| Класс             | Что внутри                                                                                  | Раскат                                                             | Влияет на симуляцию |
| ----------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------- |
| **Симуляционный** | коэффициенты пари, цены, бюджеты волн, статы врагов, Доля заведения                         | **всё или ничего**, версия целиком; смена только на границе сессии | да                  |
| **Прикладной**    | тексты, семплирование телеметрии, объявления в меню, косметические флаги, включение режимов | свободный постепенный раскат и A/B                                 | нет                 |

A/B-тесты баланса ставятся по этому же принципу: сравниваются не одновременные группы, а последовательные версии конфига. Медленнее, зато мультиплеер остаётся целым.

Версия симуляционного конфига входит в хеш совместимости лобби и в сид дейли; дейли фиксирует её на сутки, иначе рекорды за день несопоставимы.

### 8.4 Совместимость версий в кооп-игре

Для игры, в которую играют с друзьями, «мы не можем зайти вместе, потому что у меня обновилось» — это отказ продукта, а не мелкое неудобство.

- **Детерминизм означает, что кросс-версионная игра невозможна в принципе.** Разные сборки — разные миры. Обманывать себя совместимостью нельзя.
- Поэтому: понятное сообщение при рукопожатии («у Пети версия 0.9.2, у тебя 0.9.1 — обновись и позови снова»), а не безмолвный десинк.
- **Обновление никогда не прерывает начатую сессию.** Steam обновляет при запуске; веб-версия применяет новую сборку при следующем открытии, а не посреди забега.
- **Минимальная поддерживаемая версия** объявляется сервером: клиенты ниже неё не участвуют в лидербордах и матчмейкинге, но продолжают играть офлайн.
- Симуляционные обновления выкатываются **на границе суток**, вместе со сменой дейли-сида — так меньше шансов застать друзей в разных версиях посреди вечера.

### 8.5 Каналы и откат

```
nightly  → внутренний, каждый коммит в main
staging  → публичная beta-ветка (Steam) / отдельный адрес (веб), плейтестеры
live     → все игроки
```

**Процедура отката — самая важная часть доставки.** Она должна быть отрепетирована до релиза, а не изобретаться в момент аварии:

| Что сломалось    | Откат                                                                                       | Время  |
| ---------------- | ------------------------------------------------------------------------------------------- | ------ |
| Числа баланса    | вернуть предыдущую версию конфига в админке                                                 | минуты |
| Логика в сборке  | назначить предыдущий билд живым (Steam это поддерживает); веб — вернуть предыдущий манифест | часы   |
| Рантайм Electron | отдельное депо, откатывается независимо от кода игры                                        | часы   |

### 8.6 Веб-сборка — во время альфы это и есть продукт

С 0.5.0 по 0.9.0 веб-версия — единственный способ, которым люди играют, поэтому доставка там не «на потом»:

- Контент-хешированные файлы, service worker с фоновым обновлением. Из кеша он отдаёт только файлы с хешем в имени; для остального сеть идёт первой, а кеш остаётся запасным путём ради офлайна.
- **Проверка версии при запуске:** клиент сравнивает КОММИТ своей сборки с тем, что отдаёт манифест, — а не строку версии: на проде манифест пишет deploy-kit, и его метка релиза с нашей версией не совпадает никогда. Несовпадение — мягкое требование перезагрузиться, потому что старый клиент с новым симуляционным конфигом даст расхождение.
- Ненавязчивый индикатор «доступна новая версия» вместо принудительной перезагрузки посреди игры.
- Предыдущая сборка остаётся доступной по адресу — это и есть механизм отката.
- Версия и git-SHA зашиты в билд и видны в отладочном оверлее и в баг-репортах.

**Всё это работает с 0.1.0, а не с 0.5.0.** Разработчик и агент перезагружают страницу постоянно, и устаревший бандл в кеше даёт фантомные баги, которые ищешь часами.

### 8.6А Адреса и раздача

| Адрес                | Что отдаёт                            | Ветка   |
| -------------------- | ------------------------------------- | ------- |
| **`die.samoy.love`** | лендинг и играбельная сборка          | `live`  |
| `dev.die.samoy.love` | nightly для разработки и агента       | `main`  |
| `localhost:5173`     | `npm run dev` с горячей перезагрузкой | рабочая |

Раздаёт nginx на том же VPS (§3А): статика с длинным кешем на хешированных файлах и `no-cache` на `index.html` и манифесте версии — иначе проверка версии не сработает. Конфигурация и порядок первого выката — в [DEPLOY.md](DEPLOY.md).

Деплой идёт только через [deploy-kit](https://github.com/tr0llex/deploy-kit) — копирование каталога и переключение симлинка; предыдущий каталог остаётся рядом, поэтому откат — это переключение симлинка обратно. Своих скриптов выкатки в проекте нет. Отдельный домен не покупается: поддомен на личном домене владельца снимает продления и лишние расходы, а вся навигация идёт через Steam и прямые ссылки.

### 8.7 Практики, без которых дельта-патчинг не работает

Дельта-патчинг Steam ломается от мелочей, поэтому требования конкретны:

1. **Воспроизводимая сборка:** одинаковый вход даёт побайтово одинаковый выход. Фиксированный порядок модулей, никаких таймстампов и абсолютных путей в артефактах, `SOURCE_DATE_EPOCH`.
2. **CI собирает дважды и сравнивает хеши.** Если сборки разошлись — сломан детерминизм сборки, и все патчи будут весить как полная установка.
3. Неизменившееся не перепаковывается: аудио и рантайм не трогаются при патче кода.
4. Стабильные имена файлов в Steam-сборке (контент-хеши только в вебе).
5. Никакого сжатия внутри артефактов — сжимает сам Steam, а сжатый файл ломает дельту.

### 8.8 Размер и ритм обновлений

| Тип обновления               | Размер                   | Частота                                       |
| ---------------------------- | ------------------------ | --------------------------------------------- |
| Правка баланса               | **0 МБ** (remote config) | по необходимости                              |
| Патч логики или контента     | 1–5 МБ                   | раз в 1–2 недели                              |
| Обновление аудио             | до 40 МБ                 | редко                                         |
| Обновление рантайма Electron | ~150 МБ                  | ежеквартально и при security-релизах Chromium |

Версия Electron **пиннится и обновляется по расписанию**, а не подтягивается случайно вместе с зависимостями — иначе игрок получает стопятидесятимегабайтную загрузку ради правки одного коэффициента.

### 8.9 Игрок должен видеть, что изменилось

Патчноуты на странице Steam читают единицы. Поэтому — экран «что нового» при первом запуске после обновления: три пункта человеческим языком, кнопка «понятно», без модальных окон в середине игры. Для игры, которая живёт на балансных правках, это ещё и способ показать, что проект жив.

## 9. Сохранения

- Локальный JSON со **схемой версий** + миграции `v1→v2→v3`. Ни одна миграция не удаляется — сейв двухлетней давности должен открыться.
- **Steam Cloud — полная синхронизация профиля между устройствами** (ПК ↔ ноутбук ↔ Steam Deck): мета-прогресс, Ключи и разблокировки, косметика, настройки (включая ремап и доступность), профиль «Туз помнит», статистика, незавершённый соло-забег. Игрок садится за другое устройство и продолжает ровно с того места.
- Разрешение конфликтов: «больше ключей — новее», при спорных случаях — выбор игроку с показом обоих профилей (дата, Ключи, забеги).
- **Достижения** — Steam Achievements. Счётчики Steam Stats используются только как их техническая основа (накопительные ачивки вроде «выполни 500 пари»); игроку они не показываются — для этого есть внутриигровой экран статистики ([GDD §19](GDD.md)), который живёт в профиле игрока и синхронизируется Steam Cloud вместе с остальным.
- **Rich Presence** показывает друзьям «Этаж 2, ставка ×12».
- Веб- и Steam-профили независимы; при первом запуске Steam-версии предлагается одноразовый импорт локального профиля веб-альфы (код экспорта).
- **Сейву не доверяют лидерборды** — только серверная валидация реплея.
- Резервная копия предыдущего сейва всегда рядом (`save.bak`).

## 10. Структура репозитория

```
/packages
  /sim          — ядро: детерминированная симуляция, 0 зависимостей
  /shared       — типы, схемы событий, протокол, конфиг
```

## 11. Данные вместо кода

Пари, враги, апгрейды, волны, барки Туз — **JSON со схемой** (Zod), а не код. Даёт:

- балансировку без программиста и без сборки;
- валидацию данных в CI;
- редактор в админке;
- потенциальный моддинг (пари от сообщества — дешёвый UGC);
- Monte-Carlo перебор вариантов баланса.

Поведение врагов и условия пари остаются кодом (это логика), но все **числа** — данные.

## 12. Тестирование

| Вид                | Что покрывает                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Юнит (Vitest)      | fixed-point математика, RNG, экономические формулы                                                  |
| **Golden-реплеи**  | детерминизм; 20 забегов × 3 ОС в матрице CI                                                         |
| Симуляционные      | headless-прогон 10 000 забегов ботами: нет зависаний, нет недостижимых комнат, экономика в границах |
| Сетевые            | искусственные потери 5%/задержка 150 мс/джиттер: десинков ноль за 1000 матчей                       |
| Производительность | худшая волна на минимальном железе держит 60 FPS                                                    |
| Ручные             | чеклист на версию + внешние плейтестеры                                                             |

**Monte-Carlo балансировка** — отдельно ценно: бот играет 100 000 забегов с разными стратегиями ставок, и мы видим, доминирует ли верхний аппетит, разоряет ли долг, какие пари слишком лёгкие. Балансировать вслепую не придётся.

## 12А. Репозиторий и рабочий процесс

**Приватный репозиторий на GitHub** на всём протяжении разработки.

**Почему приватный до релиза:** исходники детерминированной симуляции — это и античит-модель, и полная карта баланса. Публичный репозиторий отдаёт валидацию реплеев на изучение, а страницу Steam лучше открывать трейлером, а не незаконченным кодом. Открытие части кода после релиза — отдельное решение, которое ничего не стоит принять позже и невозможно отменить, если открыть рано.

### Устройство

|              |                                                                                           |
| ------------ | ----------------------------------------------------------------------------------------- |
| Видимость    | private, весь период разработки                                                           |
| Ветки        | `main` всегда зелёная и собираемая; работа в `feat/*` и `fix/*`                           |
| Слияние      | только через Pull Request с зелёным CI, даже в одиночку — история решений важнее скорости |
| Теги         | `v0.1.0` и далее на каждую минорную версию, с заметками                                   |
| Секреты      | GitHub Secrets и `.env` на VPS; в репозитории только шаблоны `.env.example`               |
| Защита ветки | запрет push в `main` напрямую, обязательные проверки                                      |
| LFS          | для аудио и маркетингового арта; код и данные — обычным git                               |

### Что лежит в репозитории

Код, данные баланса (JSON), сценарии тестов, golden-реплеи, промты генерации ассетов, документация, конфигурация CI. **Не лежит:** ключи, сборки, сырые записи звука до обработки, персональные данные из телеметрии.

### Гигиена одиночной разработки

Практики, которые кажутся избыточными для соло, но окупаются на длинной дистанции:

- **Pull Request с описанием даже на свои изменения** — через полгода это единственный способ вспомнить, почему число стало таким.
- **Одна версия — одна веха**, тег и заметки. Заметки пишутся для себя будущего.
- **Пост-мортем каждой минорной версии** прямо в репозитории: что заняло дольше плана и почему.
- **Ветка не живёт дольше нескольких дней** — иначе слияние превращается в отдельный проект.

## 13. CI/CD

GitHub Actions в приватном репозитории (см. §12А).

```
PR:      lint → typecheck → границы модулей → unit → golden-реплеи (3 ОС)
         → сценарии → инварианты → бандл без отладочного API → секреты → сборка веб
main:    всё выше → nightly-сборка веб  [с 0.10.0: + Electron win/mac/linux → подпись]
ночью:   10 000 ботовых забегов → ограничители G1–G17, D1–D10 → отчёт баланса
tag:     всё выше → butler (itch)       [с 0.10.0: + steamcmd] → Sentry release + sourcemaps
вручную: поиск оптимума конфигурации (см. SIMULATION.md), ~ночь на 8 ядрах
```

Ночной прогон отделён от PR намеренно: тысячи забегов занимают минуты, и держать их на каждом коммите значит перестать коммитить.

До 0.10.0 конвейер целиком веб-ный: собирается один бандл, выкладывается на itch. Строки в квадратных скобках включаются вместе с оболочкой Electron.

- Подпись Windows (сертификат OV/EV — иначе SmartScreen пугает игроков), нотаризация macOS.
- Артефакты билдов хранятся 90 дней — чтобы можно было воспроизвести любой баг-репорт.
- Версия и git-SHA зашиваются в билд и уходят в телеметрию.
