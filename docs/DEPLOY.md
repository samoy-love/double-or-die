# Double or Die — выкатка

_Что уже готово, что требует доступа владельца и в каком порядке это делается._

Выкатка идёт только через [deploy-kit](https://github.com/samoy-love/deploy-kit).
Своих скриптов деплоя в проекте нет.

---

## Цели

| Цель   | Адрес            | Корень на сервере | Конфиг nginx |
| ------ | ---------------- | ----------------- | ------------ |
| `game` | `die.samoy.love` | `/var/www/die`    | ставит       |

Цель одна. Каждый коммит в `main` уезжает на прод; отдельного nightly-стенда
нет — сборку до игрока проверяют гейты выкатки, а не второй домен.

---

## Что уже сделано

- Описание цели: `.deploy-kit/game.env`
- Пайплайн выкатки: `.github/workflows/deploy.yml` — вызывает переиспользуемый
  `static-site.yml` из deploy-kit
- Конфигурация nginx: **`deploy-kit/nginx/sites/die.samoy.love.conf`**
  и сниппет `deploy-kit/nginx/snippets/samoylove-die-headers.conf`
- Манифест версии: `dist/version.json` собирается на каждой сборке, по нему
  проверяется и обновление у игрока, и совпадение выкаченного с собранным

**Гейты выкатки прогоняются и проходят:** `npm run check && npm test &&
npm run build && npm run check:no-debug-api`. Проверено в реальном запуске
пайплайна — до шага SSH доходит зелёным.

## Доступ и инфраструктура

Всё нижеперечисленное настроено; здесь оно записано затем, чтобы восстановить
состояние, не разбираясь заново.

**Сервер.** `207.127.93.34`, пользователь выкатки `ubuntu`, nginx 1.24.
Наружу домены смотрят другим адресом — это тот же хост.

**DNS.** Зона `samoy.love` в Cloudflare, `die.samoy.love` — проксируемая
запись: TLS для игрока терминирует Cloudflare, на сервер она ходит по HTTPS.
Имена второго уровня (`x.die.samoy.love`) не заводить: подстановочный
сертификат Cloudflare `*.samoy.love` их не закрывает, и за прокси такое имя
не открывается вовсе. Что ещё нужно серверу за прокси — в `nginx/README.md`
deploy-kit, раздел «Cloudflare».

**Сертификат.** Выпущен webroot-проверкой через `/var/www/die-acme`,
продлевается сам:

```bash
certbot certonly --webroot -w /var/www/die-acme -d die.samoy.love
```

**Конфигурация nginx.** Домен описан файлом
`nginx/sites/die.samoy.love.conf` в deploy-kit плюс сниппет заголовков
`samoylove-die-headers.conf`. Применяется только через `nginx-apply.sh`,
руками в `/etc/nginx` не ходим:

```bash
sudo /opt/deploy-kit/nginx-apply.sh --app die --conf /tmp/die.samoy.love.conf      --dest /etc/nginx/sites-available/die.samoy.love.conf --enable
```

Порядок здесь важен и однажды уже стоил бы отката: полный конфиг ссылается на
сертификат, поэтому до его выпуска `nginx -t` не проходит. Сначала временный
HTTP-конфиг с одной ACME-локацией, потом сертификат, потом полный конфиг.

**Секреты репозитория.** `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`,
`SSH_HOST_KEY` заданы. Ключ хоста снят с самого сервера, а не `ssh-keyscan`:
keyscan доверяет первому ответу и молча принимает подмену.

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` здесь не нужны: о релизе объявляет
бот, а не выкатка (см. ниже).

### Кто объявляет о релизе

Не выкатка, а бот `samoy-status`. Он опрашивает `/version.json` каждую минуту,
видит смену версии и пишет в чат сам — поэтому сообщения приходят, хотя токен
Telegram задан ровно в одном репозитории из шести.

Отсюда `NOTIFY=never` в обеих целях. Заведи мы токен и здесь, на каждый релиз
приходило бы ДВА сообщения об одном и том же. Голос один — бот, а выкатка
молчит осознанно, и молчание задано явно: пустой секрет пайплайн считает
недосмотром и ругается предупреждением «о релизе никто не узнал».

Чтобы бот знал про игру, она заведена в `config/status.json` репозитория
`samoy-status` — там же живут проверки сайта и сертификата.

### Про nginx в описаниях целей

Конфиг ставится парой `NGINX_CONF` + `NGINX_DEST`, и одна половина без другой
означает не «частично настроено», а молча пропущенный шаг: deploy-kit просто
не трогает nginx.

## Порядок первого выката

1. Запустить выкатку вручную с `dry-run: true` — проверить, что цель собирается и доезжает.
2. Запустить по-настоящему.
3. Убедиться, что `/version.json` на проде совпадает с собранным. «Зелёный деплой со старыми файлами» ловится именно здесь.

## Два манифеста и зачем их два

| Адрес           | Кто пишет   | На какой вопрос отвечает   |
| --------------- | ----------- | -------------------------- |
| `/version.json` | deploy-kit  | какой релиз сейчас выкачен |
| `/build.json`   | наша сборка | какая это версия игры      |

Раньше оба файла назывались одинаково, и наш просто затирался при каждой
выкатке. Работа пропадала молча, а версия игры не публиковалась вообще нигде —
правило «версия проверяется после выкатки» проверить было нечем.

Форматы разные, и это важно для клиента:

| Поле        | наш (`build.json`) | deploy-kit (`version.json`)       |
| ----------- | ------------------ | --------------------------------- |
| `version`   | `0.1.0`            | `release-20260803-165343-ba4f3c9` |
| `commit`    | короткий SHA       | короткий SHA                      |
| `changelog` | нет                | темы коммитов релиза              |

Отсюда правило: **клиент сверяет `commit`, а не строку версии.** Метка релиза
меняется при каждом выкате и с нашей версией не совпадает никогда — сравнение
по ней объявляло бы обновление на каждой проверке.

Клиент спрашивает `/version.json`, а при ответе 404 — `/build.json`. Второй
адрес нужен для локального просмотра собранной игры: deploy-kit там не
участвует, манифеста релиза нет, и без запасного пути проверка обновлений
молчала бы всегда.

Ровно здесь и жил дефект, доживший до первой выкатки: клиент искал поле
`build`, которого в манифесте deploy-kit нет. Проверка ходила на сервер,
получала `undefined` и молча решала, что обновлений нет. Закрыто тестом
`tests/update-check.test.ts` на обоих форматах сразу.

## Проверки после выката

```bash
curl -sI https://die.samoy.love/ | head -20
curl -s  https://die.samoy.love/version.json   # метка релиза
curl -s  https://die.samoy.love/build.json     # версия игры
curl -sI https://die.samoy.love/assets/ | grep -i cache-control   # immutable
curl -sI https://die.samoy.love/version.json | grep -i cache-control  # no-store
curl -sI https://die.samoy.love/sw.js | grep -i cache-control     # no-cache
```

Три правила кэширования, которые ломаются молча и потому проверяются явно:
ассеты с хешем в имени кэшируются на год, манифест версии не кэшируется
вовсе, а service worker кэшировать нельзя ни в коем случае — устаревший
воркер запирает игрока на старой версии навсегда.
